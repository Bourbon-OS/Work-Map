# Mapを使い始める時に揃えるもの

導入時に使う補助資料です。すでに渡されている情報はそのまま使い、毎回の記入や読直しは要りません。

## 接続情報を一度渡す

導入する担当は、次の実値を、既存の引継ぎ案内など一か所から分かるようにします。この表のために新しい設定ファイルを作る必要はありません。

| 情報 | 渡す内容 |
|---|---|
| プログラム | 完全な配布一式の場所と起動方法。実行するファイルの絶対パス |
| Map | 新規作成か既存Mapか、DBの絶対パス、backend（SQLiteなら`sqlite`）。既存Mapへ空のMapを作り直さない |
| 根拠資料 | `repo:`で始まる参照を解決する基準フォルダ（`docs`の親）。プログラムと別の場所なら両方を明示する |
| 担当 | 操作を記録するactor ID。OwnerとAI担当を区別し、依頼者が認めたIDを使う |
| 仕事と許可 | 今回の対象、依頼者の実際の指示、行ってよい範囲と根拠の所在 |
| 最初の読取り | その場所で実行できるコマンド。`project_id`は新規作成後または既存Mapの読取りで確認し、人が作らない |

個人向け配布版は`python C:\WorkMapPersonal\workmap.py --map-dir C:\Maps\Example show`のように、プログラムを共用し、Mapのフォルダを指定して使えます。そのMapの`data/workmap.sqlite3`と`docs`が対象です。`--map-dir`を省略すると、従来どおりプログラムのフォルダを使います。GUIで別Mapを選んでも、コマンドの対象は変わりません。新規作成とPythonの準備は、配布版の`USAGE.md`を使います。

導入担当からMap別の起動ファイルが渡されている場合は、それを普段の入口にします。そこにプログラム・DB・根拠の実値を渡せば、コード一式を複製せずに使えます。標準位置と異なる既存DBは`--map-dir`で作り直さず、次のようにDBと根拠を明示します。値はその環境の実値に置き換えます。

```powershell
$wm = 'C:\WorkMapPersonal'
$mapRoot = 'C:\Maps\Example' # docsの親
$mapDb = 'C:\Maps\Example\data\workmap.sqlite3' # 既存DBの実際の場所
$env:PYTHONPATH = "$wm\src;$wm"
Set-Location -LiteralPath $wm
python -m tools.read_workmap_store --backend sqlite --store $mapDb --evidence-repo $mapRoot --tree --work W0 --brief --compact
```

SQLiteのDBと根拠はMapごとに分け、プログラム一式をMapごとに複製する必要はありません。既存の保存場所をまとめ直す操作は自動では行いません。

個人CLIは`--map-dir`から標準DBと根拠を選び、担当は`--actor`で指定します。module入口では同じ情報を`--store`／`--backend`／`--evidence-repo`／`--actor`へ、GUI moduleでは`--store`／`--evidence-root`／`--operator-id`へ渡します。既定のOwner IDに頼らず、AIには渡された本人IDを使います。

## 手で作るもの、プログラムが作るもの

| ファイル | 用意する方法 |
|---|---|
| プログラム一式 | 配布一式を置く。足りないモジュールを利用者が手書きしない |
| SQLite DB | `init`で初めて作る。既存Mapは同じ保存先を指定する |
| Owner指示の根拠 | 新規のMap作成・Work登録・許可設定などでは、`--owner-instruction`に渡した実際の指示を保存する。GUIなどで資料を選ぶ時は、その実際の資料を指定する |
| GUIの接続一覧 | GUIが保存する。Mapの現在値を写す別正本ではない |
| 詳細な結果・根拠 | 必要になった実際の資料を使う。同じ資料や進捗メモを毎回作り直す必要はない |

AIの案はAIの案として扱います。Ownerが採用した事実がないものを、Owner指示のファイルへ変えて保存しません。

## 最上位のWorkを考えるヒント

最上位のWorkは「このMapで何を扱うか」を表せば始められます。名前・目的・きっかけを最初から完璧に決める必要はありません。次は一つの書き方で、使い方の制限ではありません。

| 項目 | 書く内容 | 例 |
|---|---|---|
| Name（名前） | 見て区別できる活動の名前 | 注文の受付を続ける |
| Intent（目的） | 何ができる状態にしたいか | 注文を取りこぼさず、担当交代後も無理なく受付を続けられる |
| Origin（生まれたきっかけ） | なぜこのWorkが生まれたか。実際の出来事・相談と出所 | 注文がメールと紙に分かれ、担当交代時に未対応を探す必要が出たため。最初の相談資料へ参照 |

「受付表を作る」を最上位の目的にすると、表を作ったところで目的を達成したように見えるかもしれません。この例なら、表の改善も、別の受付方法の検討も、目的に役立つ子Workとして考えられます。Originは、後で目的を読み直す時に、最初に何を気にしていたかを思い出す手掛かりになります。相談の全文をここへ写す必要はありません。

小さな作業、検討中の案、研究、暮らし、継続するサービスなどもWorkです。上の例に合わせるために活動を作り直す必要はありません。同じ目的を分かりやすくする訂正と、別の目的へ変える判断は区別し、必要な根拠を残します。
